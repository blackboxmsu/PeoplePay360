Employee &amp; Contract
- Employees should be viewable in both Kanban and List views.
- Opening an employee should show their HR details and related records such as Contracts,
Attendance, Time Off, and Allocations.
- An employee can have multiple contracts over time.
- Payroll should use the contract applicable to the selected payroll period.
Working Schedule
- Working Schedules need List and Form views. Clicking a row should open that schedule.
- List should surface name, calendar type, days/week, hours/week, company and status.
- Form defines the weekly pattern: day, start/end time, optional break and hours. Weekly
hours should be derived from the schedule.
- A schedule can be assigned to an Employee/Contract and used by Attendance and Payroll.
Shift, flexible-time and other rules are open to the participant.
Attendances:
- Attendance can be accessed globally or from an individual employee.
- Store check-in, check-out, worked hours, and attendance status.
- When opened from an employee, only that employee’s attendance should be shown.
- Attendance data should be usable later for reporting/dashboard insights.
Time Off:
- Requests should support a simple approval flow.
- For leave types that require allocation, approved leave should reduce the
employee’s available balance.
- Time Off Types should define how each leave type behaves. The exact
policies and validations are open to interpretation.

Payrun Creation:
Creating a Payrun happens in two steps:
- Select the payroll scope, such as employee type, salary structure, and period.
- Select the employees to include.
- Continue only moves to employee selection. A Payrun is created only after clicking “Create
Payrun”.
Only the selected employees should be included in that Payrun.
Payruns &amp; Payslips:
A Payrun represents payroll processing for a particular period.
Each selected employee should have a Payslip linked to the Payrun.
Computing payroll should use the employee’s applicable contract and selected salary structure.
Payslips should show understandable components such as Basic, Allowances, Deductions, Gross,
and Net Salary.
Payroll issues, such as missing required information or duplicate payslips, should be visible to the
user.
Payroll Workflow:
The intended flow is broadly:
Draft → Compute → Validate → Mark Paid
Paid/finalised payroll should remain available as historical data.
Salary Structures &amp; Salary Rules:
A Salary Structure contains the rules used to calculate salary.
Salary Rules can represent Basic Salary, Allowances, Deductions, Gross, Net, etc.
Rules should be processed according to their sequence.
Different calculation methods may be supported, such as fixed amounts, percentages, or formulas.
Participants are free to design the calculation engine as long as salary rules actually drive Payslip
calculations.
Payslip PDF:
Users should be able to generate/print a Payslip showing the employee’s payroll calculation for
that period.
Sending Payslips can also be supported from the Payrun.
Payroll Dashboard:
The dashboard should use actual data created through the HR and Payroll flows rather than
hardcoded values.
It should provide useful payroll/HR insights such as:
Salary totals
Payslip status
Salary by department
Salary trends
Attendance overview
Time Off overview
Payroll warnings or items requiring attention
Filters such as Period, Department, Employee Type, or Company should affect the relevant
dashboard data.

Computation Note:
- Fixed Amount: uses the exact value entered in the rule, e.g. Meal Allowance = 2,000.
- Percentage: calculates the rule as a percentage of a selected base such as Contract Wage,
Basic Salary, or Gross Salary, e.g. HRA = 20% × Basic Salary.
- Python Code / Formula: is used for advanced calculations where fixed or percentage methods
are not sufficient, such as attendance-based salary, overtime, unpaid leave deductions, or
calculations using multiple salary-rule values.
